## 二、架构决策

### 2.1 为什么拆？

**痛点**：
- `index.ts` 2847 行，单文件承担路由定义、业务逻辑、初始化、WS 服务器四重职责
- 路由端点分散在文件各处，难以定位和维护
- 每次改一个小功能都要在 3000 行里跳来跳去
- 新人接手成本高，容易改错

**收益**：
- 职责单一：`index.ts` 只做初始化和挂载，业务逻辑全在 `src/routes/`
- 模块独立：每个路由文件可独立测试、独立 review
- 可读性提升：从"在 3000 行里找路由"变成"看 `src/routes/` 目录就知道有哪些功能"
- 维护成本降低：改一个功能只动一个文件，影响面可控

### 2.2 怎么拆？

**原则**：
1. **按功能域拆分**：不是按行数机械切，而是按业务逻辑聚类（如 wallet/credits 一起拆，agents/subagents 一起拆）
2. **保持挂载顺序**：路由挂载顺序影响 Express 匹配优先级，拆分后必须保持原顺序
3. **补全鉴权**：拆分过程中发现部分路由缺少 `requireAuth`，顺手补上（安全加固）
4. **双验证闭环**：每次拆分后必须通过 `tsc --noEmit` + 路由快照 + 冒烟测试三连验证

**工具链**：
- `scripts/route-snapshot.mjs`：路由快照，记录所有端点的 method + path + handler 位置
- `scripts/smoke-mount.mts`：挂载完整性校验，确保 import 必须配对调用，杜绝死路由
- 自动化补丁脚本：每个批次生成 `_patch-bXX.mjs`，记录拆分操作，可追溯可回滚

### 2.3 为什么保留 3 个内联端点？

`/api/health`、`/api/version`、`/api/logs` 留在 `index.ts`，原因：
- 这 3 个是**基础设施端点**，不依赖业务逻辑
- 健康检查需要在服务启动最早期响应，不适合走路由模块
- 版本和日志是运维端点，和入口生命周期强相关
- 强行拆出去反而增加间接层，得不偿失

## 四、验证方法

### 4.1 三层验证体系

每次拆分后必须通过以下三层验证，缺一不可：

#### 层 1：类型检查
```bash
npx tsc --noEmit
```
- 零错误 = 类型安全
- 确保 import/export 正确，没有遗漏依赖

#### 层 2：路由快照
```bash
node scripts/route-snapshot.mjs
```
- 记录所有端点的 method + path + handler 位置
- 拆分前后快照对比，确保端点数量和内容一致
- 防止"路由丢失"或"路由重复"

#### 层 3：挂载完整性 + 冒烟测试
```bash
node scripts/smoke-mount.mts
```
- 校验所有 `create*Routes` 必须被 import 且调用
- 防止"死路由"（import 了但没挂载）
- 动态加载所有路由模块，验证注册成功

### 4.2 历史教训

**批次 4 的 wallet 挂载遗漏**：
- 批次 4 拆分 wallet 时，`registerWalletRoutes` 被误删
- 批次 5 快照显示"232/232 路由匹配"，但实际 wallet 路由未挂载
- 原因：快照脚本只校验文件内容，不校验运行时挂载
- 修复：批次 4.1 补回 wallet 挂载 + 快照脚本增加挂载数校验

**教训**：
- 快照不能只看文件，必须校验运行时行为
- 每次拆分后必须跑冒烟测试，确认服务能正常启动
- 路由挂载必须有 import + 调用双校验

## 六、经验总结

### 6.1 拆分策略

1. **先易后难**：从独立模块（auth、wallet）开始，逐步深入复杂模块（mesh、rag）
2. **小步快跑**：每个批次只拆一个功能域，拆完立即验证，不攒大活
3. **自动化优先**：用脚本生成补丁，避免手动修改 3000 行文件出错
4. **双验证闭环**：类型检查 + 路由快照 + 冒烟测试，三层验证缺一不可

### 6.2 踩坑记录

1. **死路由陷阱**：快照只看文件内容，不校验运行时挂载 → 增加挂载数校验
2. **shell 重定向翻车**：`echo "..." > {const` 这种语法在 PowerShell 里会创建畸形文件名 → 改用 `write_file` 工具
3. **API 限额撞墙**：连续调用 5 次失败（429 you have reached your weekly usage limit）→ 等限额恢复或升级账户
4. **战报数据失真**：中间态战报说"2103 行"，实际测量是 822 行 → 以实际测量为准，不信战报

### 6.3 给后人的建议

1. **不要怕拆**：2847 行的巨石文件看着吓人，但拆成 14 个批次，每批只动 100-300 行，其实很快
2. **验证比拆分更重要**：拆完不验证等于白拆，三层验证必须跑全
3. **保留历史记录**：补丁脚本、侦察笔记、快照文件都有价值，别删，归档就行
4. **及时 commit**：每个批次拆完立即 commit，方便回滚和追溯
