# 统一自动重试与失败自愈改造（v2.8.0）

> 对标：NousResearch/hermes-agent（MIT）的 `retry_utils.py` / `turn_retry_state.py` / `turn_loop_errors.py`
>
> 起因：用户反馈「失败后为何不自动重试」「干活一直让我点继续」「遇到限流就停下」。

---

## 一、改造前的真实病根

| 层级 | 原行为 | 造成的用户可见故障 |
|---|---|---|
| `src/ai/hub.ts` | `MAX_RETRIES=3` 写死，退避 `1000*2^(n-1)`、上限 16s、**无 jitter**、**无视 Retry-After** | 限流时立刻重撞；多任务同时重试形成惊群 |
| `src/tools/executor.ts` | 认 Retry-After，base 1s / cap 32s | 与 Hub 各算各的，一次 429 被**两层叠乘放大** |
| OpenAI SDK | `maxRetries: 1` | SDK 暗中再重试一层（共 3 层） |
| `src/core/router.ts` | 只对 `ai_errors` 退避，且写死 `backoffDelayMs(n, 2000, 15000)` | `max_iterations` / `tool_failures` 被限流拖住时**零等待**重踩 |
| `src/core/router.ts` | 续跑 `catch` 直接 `break` | **网络抖一下就整个停摆**，甩一句「输入继续」给用户 ← 这是最致命的一条 |
| `src/core/autonomy.ts` | `extractRetryAfterMs` 只支持秒数，且硬夹 120s | **Retry-After 的 HTTP-date 格式完全没被支持**；长窗口被腰斩 |

## 二、改造后的架构

```
                  ┌─────────────────────────────────────┐
   429 / 5xx ───► │  src/core/retry-coordinator.ts       │ ◄─── 全引擎唯一决策点
                  │  · classifyFailure  → 恢复模式        │
                  │  · shouldWaitAndRetry → 该不该等      │
                  │  · computeDelayMs   → 等多久          │
                  │  · runWithRetry     → 统一执行体      │
                  │  · TurnRecoveryState → 一次性守卫     │
                  └──────────────┬──────────────────────┘
                                 │
        ┌────────────────────────┼────────────────────────┐
        ▼                        ▼                        ▼
   executor.ts              ai/hub.ts              core/router.ts
   逻辑操作预算              单次 API 调用            跨轮自动续跑
```

### 恢复模式（`RecoveryMode`）

| 模式 | 触发 | 动作 |
|---|---|---|
| `same` | 429 / 5xx / 网络抖动 | 原样重试 |
| `compress` | 上下文超限 | 压缩后重发 |
| `continue-length` | 输出截断 | 续写，不从头来 |
| `rebuild` | 402 余额耗尽 / 400 payload 错 / 401 403 | 换 provider 或重建 payload |
| `redirect` | 区域封锁 | 切供应商 |
| `stop` | abort / 401 凭据 / 404 模型不存在 | 立即停 |

## 三、修掉的 3 个真 bug

这 3 个是**测试反查出来的**，不是猜的。

### Bug 1：用户点「停止」后任务仍会被复活

```ts
// src/core/autonomy.ts
if (err?.name === 'AbortError') return false;
if (err?.code === 'ABORT_ERR') return false;
```

原来 `isRetryableError` 完全不认 `AbortError`。一旦上游把 429 和 abort 混在一起
（比如 abort 时正好在退避中），引擎会借「限流可重试」的名义把用户已停止的任务复活。
**停止优先级必须高于「永不停止」的诉求。**

### Bug 2：Retry-After 的 HTTP-date 格式完全没被支持

```ts
const secs = Number(raw);                       // 'Wed, 01 Oct 2026 …' → NaN
if (Number.isFinite(secs) && secs >= 0) { … }
// ← NaN 直接落空，后面什么都不做
```

RFC 9110 规定 `Retry-After` 既可以是秒数，**也可以是 HTTP-date**。
原来只处理前者，于是服务端明确说「等 10 分钟再试」，我们 8 秒后照撞不误 ——
这正是限流恢复不了的直接原因之一。

同时把 120s 硬夹删掉：

```ts
return Math.max(0, secs * 1000);   // 解析层如实还原
// 封顶统一由 computeDelayMs 的 maxSleepMs 负责
```

双重封顶会让调用方误判：服务端说 3 小时，调用方拿到 2 分钟，提前醒来再撞一次。

### Bug 3：Router 续跑「一失败就 break」

```ts
// 改后
const fatal = signal?.aborted
  || resumeErr?.name === 'AbortError'
  || !shouldWaitAndRetry(resumeErr);

if (fatal) { break; }               // 致命：必须停
// 可恢复：退避后自动重试
const { delayMs } = computeDelayMs(resumeErr, resumeRounds, budget);
await sleep(delayMs);
continue;
```

配套新增 `synthRetryError()`：executor 的 `result.error` 是 **string**，
没有 `statusCode`/`headers`，直接喂给分类器会全落进「未知错误」，
于是 429 被误判成致命而不再重试。这个函数按 `stopReason` 反查可信的 HTTP 语义：

| stopReason + 文案特征 | 合成 status |
|---|---|
| `401` / `invalid api key` | 401（致命） |
| `403` / `forbidden` | 403（致命） |
| `404` / `model not found` | 404（致命） |
| `429` / `rate limit` / `quota` / `overloaded` | 429（可恢复） |
| `timeout` / `ECONNRESET` / `fetch failed` | 网络错误（可恢复） |
| `5xx` / `bad gateway` | 503（可恢复） |

顺序刻意把 401/403/404 排在 429 前面 —— 限流网关偶尔在正文里带 401 字样。

## 五、验收结果

```
tsc --noEmit          0 错误 ✅
vitest run            106 passed / 106 ✅  （6 个测试文件）
```

覆盖的关键场景：

- 429 前两次失败、第三次成功 → 自动走完，**不甩锅给用户**
- 重试耗尽 → `ok=false` 且带原始错误，**不伪装成功**
- 401 → 一次都不重试（不浪费 30 秒）
- 中途 abort → 立刻停，不再重试
- AbortError 带 429 → 仍然致命（停止优先）
- 服务端要求「4 小时后重置」→ 封顶在 `maxSleepMs`，**绝不真睡 4 小时**
- jitter 确实产生不同值（防惊群，不是写死常数）

## 七、还没做的（诚实列出）

1. **多轮自动恢复预算（`TurnRecoveryState.autoRecoveryCycles`）已实现但未接入 Router 主循环** —— 目前只用到 `classifyFailure` / `computeDelayMs` / `shouldWaitAndRetry`。
2. **`compress` / `continue-length` / `redirect` 三种恢复模式未接执行端** —— 分级函数能正确识别，但真正执行动作的代码在 executor，不在本轮范围。
3. **没有跨进程恢复检查点** —— 进程崩溃后任务状态仍丢失，Hermes 的 `turn_retry_state` 是内存态，我们还没有持久化。
4. **未做真实限流压测** —— 单元测试用 mock 构造 429，未在真实供应商上验证。
