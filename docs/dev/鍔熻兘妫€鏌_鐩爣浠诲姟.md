# 🎯 目标任务：「灵犀引擎功能检查」

## 一、目标定义

**目标名称**：灵犀引擎功能检查（聚焦功能是否正常、尽量多查）

**核心意图**：不追求"查完所有 bug"，而是对灵犀引擎的核心模块做一次**可穷举、可验收**的功能走查，确认每个功能点是否正常走通，并系统性暴露数据流断裂和认证/错误处理缺陷。

---

## 二、范围界定

### ✅ 检查范围（本目标覆盖）

| 模块 | 说明 |
|------|------|
| 目标任务系统（Goals） | 核心，6 个功能点全查 |
| 工作流（Workflows） | 读操作认证 + 功能走查 |
| 成果（Outcomes） | 路由认证 + 数据流 |
| 数据流一致性 | 前端 app.js → API 路由 → 后端逻辑 → DB → 前端渲染 |
| 认证与错误处理 | 关键路由的 requireAuth 覆盖 + try-catch 空吞 |

### ❌ 不在范围（本目标不查）

| 排除项 | 原因 |
|--------|------|
| 代码规范/风格/重构建议 | 非功能问题，噪音大 |
| 性能压测/并发测试 | 超出"功能是否正常"范畴 |
| 第三方依赖漏洞扫描 | 独立的安全审计范畴 |
| P2 以下体验细节（按钮颜色、文案错别字等） | 按缺陷分级过滤，避免噪音 |
| Chat/Auth 模块的深度逻辑审查 | 本次聚焦目标系统，可作为下一轮目标 |

---

## 三、验证方式（两种并用）

1. **静态代码审查**（主）：逐行追踪前端函数 → API 路由 → 后端 handler → DB 读写 → 响应字段 → 前端渲染，验证数据流是否完整闭合。
2. **动态验证**（辅，有条件时）：若沙箱可启动服务，对关键端点发送真实 HTTP 请求（未认证请求 / 认证请求 / 非法 ID），验证认证拦截与错误返回是否符合预期。

> 注：第三方 AI 调用、WebSocket 推送等依赖外部服务的链路，静态审查无法覆盖运行时表现，报告中单独标注「未动态验证」。

## 四、缺陷分级标准

| 级别 | 定义 | 处理要求 |
|------|------|----------|
| 🔴 P0 | 阻断性：功能完全不可用 / 未认证可读敏感数据 / 崩溃 | 必须列出复现步骤 + 修复建议 |
| 🟠 P1 | 功能性：功能部分可用、行为与预期不符、静默失败 | 必须列出复现步骤 + 修复建议 |
| 🟡 P2 | 体验性：错误提示缺失、日志缺失、边界未处理 | 列出清单即可，附建议 |
| ⚪ P3 | 规范类：命名、风格、重构建议 | **不收录**（超出范围） |

---

## 五、状态判定标准（任务 1 用）

| 状态 | 判定条件 | 示例 |
|------|----------|------|
| ✅ 正常 | 前端有入口 → 后端有路由 → 数据流闭合 → 有返回/反馈 | 添加目标完整走通 |
| ⚠️ 部分 | 功能链路存在但受限：仅在特定条件下生效，或后端有接口但前端入口缺失 | 开始目标仅对 project-* ID 生效 |
| ❌ 不可用 | 用户无法触达 / 调用必失败 / 数据流断裂 | 反向提问无前端入口 |

## 七、子任务拆分

### 任务 1（优先，约 30 分钟）：逐功能走查目标任务系统

逐一操作 6 个功能点，记录是否能正常走通：

1. ① 添加目标
2. ② 开始目标
3. ③ 标记完成
4. ④ 删除目标
5. ⑤ 反向提问
6. ⑥ 目标进度在对话中可见

每个功能给出 ✅/⚠️/❌，非 ✅ 的附带复现步骤。

### 任务 2（约 1 小时）：数据流一致性审查

追踪前端 app.js 目标相关函数 → API 路由 → 后端处理逻辑 → 数据库读写 → 返回前端渲染，标记：
- 参数名不一致（如 projectId 格式）
- 状态转换遗漏
- 静默失败
- 路由重复定义/遮蔽

### 任务 3（约 20 分钟）：关键路由认证和错误处理

- 检查 /api/goals、/api/outcomes、/api/workflows 全部端点的认证保护
- 检查 try-catch 是否吞错（catch(_) {}）
- 输出认证矩阵 + 空 catch 清单
