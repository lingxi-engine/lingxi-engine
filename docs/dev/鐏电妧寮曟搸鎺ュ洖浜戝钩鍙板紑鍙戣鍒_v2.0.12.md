# 灵犀引擎接回云平台（中心化账号体系）开发计划

- **版本目标**：v2.0.12
- **编写日期**：2026-08-14
- **关联问题**：好友请求"已发送但对方收不到"（已在本机 LAN 转发层面修复，本计划为根治方案）
- **核心目标**：恢复云平台统一注册/登录与全局唯一 ID 分配，消除跨引擎 numeric_id 冲突

---

## 一、背景与问题

### 1.1 问题现象
两台引擎互加好友时，发送方显示"已发送"，接收方永远收不到。

### 1.2 已确认根因（代码级证据）
1. **numeric_id 本地独立分配**：每台引擎从 10000 起自增（`db.ts` 中 `_nextNumericId = 10000`；`index.ts` `ensureUserSetup` 用 `MAX(numeric_id)+1`），两台引擎首个用户都是 10000。
2. **本地优先匹配吞请求**：`lan-social.ts sendFriendRequest` 先查本机 DB，命中同号用户即写本地库、不走 LAN。
3. 已通过 LAN 转发层修复（本机命中自己时强制走 LAN、接收端错误如实返回、发送失败回滚 pending），但**同号歧义无法彻底消除**——根治需要全局唯一 ID，即恢复平台中心化分配。

### 1.3 为什么 ID 是本机分配的
- v2.0.6 起前端关闭了云平台：`web/js/app.js` 第 2185 行 `const PLATFORM_URL = '';`（注释：本地部署时不走云平台）。
- `platformApi()` 实现为 `fetch(PLATFORM_URL + url)`，前缀为空 → 所有注册/登录/好友请求实际打到本地引擎。
- 每台引擎"自己当自己的平台"，各自发号，跨引擎必然重复。

## 三、方案总览

恢复前端 `PLATFORM_URL` → 注册/登录/用户身份/跨引擎好友操作全部经由云平台（47.93.157.83:8080）；本地引擎保留聊天/AI 能力，用户身份与 numeric_id 从平台同步而来。

前端所有 `platformApi` 调用点均已有本地回退逻辑（v2.0.11），平台不可达时自动降级为本地模式，**切换是安全可逆的**。

### 4.3 身份同步（本地引擎 ↔ 平台）
**问题**：平台注册的用户 id 与本地引擎的用户 id 是两套体系；本地 WS 连接以浏览器 clientId 触发 `ensureUserSetup` 自动建本地用户。

**改造点**：
1. 平台登录成功后，前端已持有平台用户 id（`/api/user/me` → `lanMeId`）；本地引擎需提供"以平台身份落地本地用户"的通道：WS 连接或专用接口携带平台 userId + 平台 token，本地引擎验证后：
   - 本地存在同 id 用户 → 更新在线状态；
   - 不存在 → 以平台 userId 为 id 创建本地用户（而非 clientId），**numeric_id 采用平台分配的值，不再本机自增**。
2. `ensureUserSetup` 仅在"无平台身份"（游客/平台不可达）时走本机分配，作为降级路径保留。
3. `/api/user/me` 本地路由需兼容返回平台身份（前端 355 行的 lanMeId 解析依赖它）。

### 4.4 numeric_id 同步
- 平台注册时由平台分配全局唯一 numeric_id；本地落地用户时直接写入该值。
- 存量本地用户（已被本机分配 10000 等号码）迁移策略：
  - 若该用户在平台也有账号 → 以平台号码为准覆盖；
  - 纯本地访客 → 保留本机号码（降级路径，与平台用户冲突概率由平台号码段规划规避，建议平台分配段与本地段区隔，例如平台 ≥100000）。

### 4.5 好友系统适配
- 本次已完成的 LAN 转发修复（lan-social.ts）**保留不回滚**：即使接入平台，两台引擎局域网直连场景仍依赖它；平台路径与 LAN 路径并存，前端已有优先级（platformApi 优先、失败回退本地）。
- 平台在线时好友数据以平台为准；`loadFriends/loadRequests` 已有回退逻辑，无需改动。

## 六、测试计划

1. **注册/登录**：新账号在平台注册 → 本地引擎出现对应身份；平台不可达时回退本地模式可用。
2. **身份一致性**：`/api/user/me`（平台）与本地 users 表 id 一致；`lanMeId` 解析正确。
3. **好友全流程**：两台引擎（不同电脑）注册平台账号 → 搜索到对方 → 发请求 → 对方收到 → 同意 → 双向出现在好友列表 → 私聊消息互通。
4. **同号场景回归**：两个平台用户数字 ID 不再重复；即使降级到本地模式，已修复的 LAN 转发仍能处理同号。
5. **断网降级**：拔断外网，前端 platformApi 全部回退本地 API，无白屏/报错卡死。
6. **存量兼容**：升级前已有本地好友关系的用户，升级后数据可见或可迁移。

## 七、风险与回滚

| 风险 | 等级 | 应对 |
|------|------|------|
| 云平台 8080 与本地引擎版本差异（平台 v2.0.8 vs 本地 v2.0.11+），端点行为不一致 | 中 | P1 阶段逐端点实测；必要时先升级云端引擎 |
| 平台与本地 JWT 密钥不一致导致 401 | 中 | JWT_SECRET_FALLBACKS 对齐；前端回退逻辑兜底 |
| 存量本地账号与平台账号映射错乱 | 中 | 迁移脚本先备份 data/main.db；号码段区隔 |
| 平台单点故障 | 低 | 前端已有全量本地回退（v2.0.11），自动降级 |

**回滚方案**：将 `PLATFORM_URL` 改回 `''` 即恢复纯本地模式，无数据破坏性变更；`.env` 改动可逆。
