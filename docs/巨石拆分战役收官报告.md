## 一、战役背景

### 1.1 问题
`src/index.ts` 膨胀至 **2847 行**，成为典型的"巨石文件"：
- 可读性差：路由、中间件、初始化逻辑、WebSocket、生命周期全部堆在一起
- 冲突频繁：多人协作时 merge 冲突密集
- 改动风险高：任何路由修改都可能误伤启动流程

### 1.2 目标
将巨石文件按**职责边界**拆分为模块化路由文件，入口仅保留**初始化 + 挂载 + WebSocket + 生命周期**，目标行数 < 1000 行。

---

## 二、架构决策

### 2.1 拆分原则
1. **按路由前缀拆分**：每个 `/api/xxx` 前缀对应一个 `src/routes/xxx.ts`
2. **工厂函数模式**：每个路由文件导出 `createXxxRoutes(ctx)` 工厂函数，接收共享上下文
3. **入口只挂载**：`index.ts` 仅 `app.use('/api', createXxxRoutes(ctx))`，不写任何路由逻辑
4. **鉴权统一**：所有路由文件内部自行调用 `requireAuth`，不依赖入口中间件

### 2.2 保留在入口的内容
- **import 区**（~80 行）：模块导入
- **接口定义 + RBAC**（~60 行）：全局类型和角色控制
- **`main()` 启动流程**（~400 行）：DB 初始化 → 平台用户同步 → AIHub/工具/浏览器/插件/定时任务/会话/审批/Hook/收件箱/技能/渠道/语音/自定义Provider/调试面板/Vision/推送 全家桶初始化
- **Express 配置 + 路由挂载**（~100 行）：全部走 `create*Routes` 模式
- **WebSocket 服务器**（~80 行）：WS 连接管理
- **优雅退出 + 端口解析**（~50 行）：生命周期管理
- **3 个内联端点**：`/api/health`、`/api/version`、`/api/logs`（入口级诊断，不值得再拆）

### 2.3 不拆的理由
- **WebSocket**：与 HTTP 路由不同层，混在一起反而清晰
- **health/version/logs**：入口级诊断端点，拆出去反而增加间接层
- **初始化流程**：强依赖执行顺序，不适合外迁

## 六、经验总结

### 6.1 成功的做法

1. **分批执行**：每批迁移一个逻辑模块，避免一次性改动过大
2. **每批验证**：三重验证（tsc + 快照 + 冒烟）确保无遗漏
3. **自动化脚本**：编写探针脚本辅助迁移，减少人工出错
4. **每批 commit**：便于回滚，历史清晰

### 6.2 踩过的坑

1. **挂载遗漏**：批次 4 的 wallet 路由因批次 5 脚本误删导致运行时未挂载（快照呈"假绿"）
   - **教训**：快照脚本必须校验挂载数，不能只看路由定义
2. **shell 重定向翻车**：多个探针脚本因 shell 重定向问题产生畸形文件名（`console.log('`、`{const`…）
   - **教训**：复杂脚本用 `write_file` 写入，不要用 shell 重定向
3. **战报数据失实**：中间态战报曾出现"2103 行、83 个内联路由"的错误数据
   - **教训**：所有数据必须现场实测，不能凭记忆

### 6.3 可复用的模式

1. **工厂函数模式**：`createXxxRoutes(ctx)` 接收共享上下文，返回 Express Router
2. **路由快照脚本**：启动前后对比路由数量、路径、方法
3. **边界断言脚本**：校验拆分前后一致性
4. **三重验证流程**：tsc + 快照 + 冒烟，每批次必跑
