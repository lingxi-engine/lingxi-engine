🍎 macOS 一行命令部署

自动识别 Apple Silicon / Intel 芯片，自动安装 Homebrew 与 Node.js，配置 LaunchAgent 开机自启，装完自动打开 http://localhost:3456。

打开「终端」（Terminal），粘贴执行：
curl -fsSL https://www.lingxi-engine.com/public/install.sh | bash
💡 常用子命令（管道执行时参数跟在 bash -s -- 后面）：
· 解除 dmg 应用拦截：curl -fsSL https://www.lingxi-engine.com/public/install.sh | bash -s -- --fix-app
· 卸载：curl -fsSL https://www.lingxi-engine.com/public/install.sh | bash -s -- --uninstall
· 关闭开机自启：加 --no-autostart；先演练不实际安装：加 --dry-run

安装脚本会自动做什么

  1. 识别操作系统与芯片架构（x86_64 / arm64）
  2. 安装 Node.js 运行时（apt / dnf / yum / Homebrew 自动分支）
  3. 下载引擎分发包（约 2.65MB）并解压到安装目录
  4. 生成 .env 配置（含随机 JWT 密钥）并安装 npm 依赖
  5. 配置开机自启（macOS LaunchAgent / Linux systemd 用户服务或 XDG autostart）
  6. 启动引擎并打开 http://localhost:3456

DGX / GPU 服务器追加步骤（本地大模型推理）

引擎装好后，如需接本地 GPU 模型：

curl -fsSL https://ollama.com/install.sh | sh

OPENAI_BASE_URL=http://localhost:11434/v1

pm2 restart lingxi-engine || sudo systemctl restart lingxi-engine

❓ 常见问题 FAQ（展开查看）

安装类

Q：curl 命令执行后没反应 / 卡住？
A：检查网络能否访问 https://www.lingxi-engine.com（公司内网可能拦截非常用端口）；macOS 用户确认用的是「终端」而非 IDE 内置受限终端。

Q：macOS 上 dmg 应用被系统拦截？
A：执行 curl -fsSL https://www.lingxi-engine.com/public/install.sh | bash -s -- --fix-app 一键解除 Gatekeeper 拦截。

Q：Linux 提示 glibc too old？
A：系统过旧（如 CentOS 7），请升级到 Ubuntu 20.04+ / Debian 11+ / CentOS Stream 8+。

Q：npm 安装很慢或超时？
A：切换国内镜像 npm config set registry https://registry.npmmirror.com 后重跑脚本。

移动端类

Q：手机端需要配置什么吗？
A：不需要配置模型、不需要装运行环境。手机只做显示和下发指令，用同一个账号登录即可。

Q：手机端会不会消耗手机算力／手机会不会发烫？
A：不会。模型推理和工具执行全部发生在引擎所在机器（你的电脑或云端服务器）上，手机不承担计算。

Q：手机登录后为什么和我电脑上的会话不一样？
A：多半是登录了不同账号。请确认手机端与电脑端使用完全相同的账号密码；另外若引擎是本地／自部署的，需确认手机访问的正是那台引擎。

Q：电脑上正在跑的任务，手机能接管吗？
A：能。同账号下任务状态共享，手机上可查看进度、继续下发指令，任务仍在引擎侧持续运行。

运行类

Q：端口 3456 被占用？
A：编辑 .env 修改 PORT 后重启；或用 ss -tlnp | grep 3456（Linux）/ lsof -i :3456（macOS）找到占用进程。

Q：怎么验证装好了？
A：浏览器打开 http://localhost:3456，或终端执行 curl http://localhost:3456/api/health，返回 ok 即成功。

Q：开机没有自启？
A：macOS 检查「系统设置 → 通用 → 登录项」；Linux 检查 systemctl --user status lingxi-engine；重跑安装脚本可修复。

Q：怎么彻底卸载？
A：curl -fsSL https://www.lingxi-engine.com/public/install.sh | bash -s -- --uninstall，会清理程序文件、自启配置和菜单图标（保留用户数据）。

Q：WSL 里能跑吗？
A：能。按 Linux 方式安装，Windows 浏览器直接访问 localhost:3456 即可。

把 DATA_DIR 设成绝对路径时，旧的 join(cwd, DATA_DIR) 拼出 <仓库>\D:\lingxi-data 这种荒谬目录， main.db 与 providers.json 各存各的 → 会话和 Provider 凭空消失 新增 src/core/paths.ts 作为唯一数据目录入口， 用 resolve() 兼容相对与绝对路径；同时支持 LINGXI_DATA_DIR / DATA_DIR / LINGXI_HOME， 未设置时从模块路径反推仓库根，不再随启动目录漂移

🛡️ v2.0.30 变更：自动重试与失败自愈

集中解决「任务失败后不自动重试」「遇到限流就停下」「一直让用户点继续」三个问题。 新增全引擎唯一的重试协调器，Executor、AI Hub、任务续跑三层统一决策， 不再各自为政地重复重试。

改了什么

原问题现在
续跑时网络抖一下，整个任务就停，并提示「输入继续」 按错误类型自动判断：限流 / 5xx / 网络抖动 → 退避后自动重试；凭据错误 / 模型不存在 → 立即停下并说明原因
三层各自重试，一次限流被叠乘放大，越撞越狠 统一由一个协调器计算重试次数与等待时长，不再叠乘
多个任务同时撞上同一个限流端点（惊群） 退避加入随机抖动，错开重试时刻
无视服务端说的「等 N 分钟再试」 完整支持 Retry-After 的秒数与 HTTP 日期两种格式，并解析主流供应商的额度重置提示；单次等待设有绝对上限，不会真睡几小时
点了「停止」，任务仍会被后台复活 用户停止的优先级高于一切自动恢复策略

升级 multer 至 2.4.0，修复上传中断导致磁盘写入堆积的 DoS 漏洞（GHSA-3pph-fpjx-jg34）。 当前 npm audit 为 0 vulnerabilities。
